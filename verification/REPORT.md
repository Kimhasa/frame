## UI 보존 (0.5 기준)

- `node tools/verify-ui-v05.mjs`: 작업 전후, 모든 빌드 후 통과("UI 0.5 passed; 0.4 references preserved"). `reference/`, `UI_LOCK.json`(0.4 원본)은 변경하지 않았고, 0.5 잠금(`UI_V05_LOCK.json`)은 Codex가 갱신한 것을 그대로 사용했습니다. 잠금 해시를 맞추려고 파일을 바꾸지 않았습니다.
- 추가 지시(0.5.1, `CLAUDE_CAPTURE_PLAYER_ADDENDUM.txt`)의 플레이어 조작부 자동 숨김은 허용된 예외로 새 파일 `work/player-ui.css` 하나에만 넣었습니다. 그래서 `verify-ui-v05.mjs`는 이제 "static markup, styles or SVG changed"를 보고합니다(의도된 차이). 원본 해시는 덮어쓰지 않았고, 새 검사 `node tools/verify-ui-v051.mjs`가 0.5 잠금 파일·0.4 원본이 그대로이고 이 CSS를 빼면 0.5 마크업 해시와 정확히 같음을 확인합니다(기록: `UI_V051_ADDENDUM.json`). 플레이어·미리보기 바깥 틀은 0.5 그대로입니다.

## 기능 검증 (이 PC)

### 내부망 영상 목록과 자동 등록
- 송출 시작 시 자동 등록, 종료 시 즉시 제거(bye) 및 7초 응답 만료. 같은 서브넷은 UDP 멀티캐스트 239.255.42.99:8899(2초 간격 알림), 다른 서브넷은 `directoryServers`로 지정한 수집 PC에 HTTP 알림. 알림의 광고 주소와 보낸 주소가 다르면 거부.
- 확인: `GET /api/broadcasts`에 실제 방송(제목 "FRAME 모션 테스트", 송출자 PC 이름, 1080p/60fps, 썸네일 URL) 표시, 썸네일 200 image/jpeg(480×270, 5초마다 갱신, 카드는 캐시된 JPEG만 표시하고 카드별 WebRTC를 열지 않음). LAN 주소로 연 Edge 목록에서 카드 클릭 → 재생.
- 멀티캐스트 수신은 이 PC의 다른 인터페이스(Tailscale)로 돌아온 자기 알림까지 확인했습니다(자기 방송으로 인식해 무시하도록 수정). **다른 PC 간 등록은 검증하지 못했습니다.**
- 송출 PC의 MediaMTX는 각 PC가 자신의 것을 실행합니다. `serverHost`는 내장 서버의 광고 주소(이 PC 주소)이며 외부 MediaMTX로 보내는 기능은 구현하지 않았습니다(README에 명시). 목록 수집 PC는 목록만 모으고 영상은 각 송출 PC에서 직접 받습니다.

### 모니터(전체 화면) 캡처
모니터 2대가 왼쪽부터 번호, 실제 썸네일, 해상도·배율(3840×2160 175% 주 모니터 / 3840×2160 150%), 장치 경로 기반 고정 ID로 표시되고, 선택하면 미리보기와 송출이 그 모니터 전체로 바뀝니다. 연결 해제 시 송출을 멈추고 알리며 다른 대상으로 임의 전환하지 않습니다(코드 경로, 실제 모니터 분리는 시험하지 않음).

### 화질·비트레이트
- 출력 해상도 = 선택한 화질(추가 지시 반영). 1080p 선택 시 창 모양과 상관없이 항상 1920×1080이고, 내용은 원본 비율로 가운데 배치(아래 표). 처음 구현(원본 비율로 출력 크기를 줄이던 방식, 예: 1816×1080)은 추가 지시에 따라 바꿨습니다.
- 자동 비트레이트 = 0.07 bit/픽셀 × 60 × (fps/60)^0.75 × 인코더 계수 → 1920×1080 60fps NVENC = 8.5 Mbps. UI 목표값 = 인코더 설정값(상한)이고 측정 비트레이트는 따로 표시. 수동 입력값은 덮어쓰지 않습니다.
- 기본 VBR(품질 우선, 상한 적용), cbr 선택 가능. 아래 저장 측정 참고.

### 저장 용량과 부하 (`tools/measure-storage.mjs`, 각 60초, 1816×1080 60fps NVENC, 상한 8 Mbps — 추가 지시 전 출력 크기 기준)

| 화면 / 방식 | 녹화 크기 | 평균 | FFmpeg CPU | FrameConsole CPU | MediaMTX CPU | GPU / 인코더 |
| --- | --- | --- | --- | --- | --- | --- |
| 정적 글자 / VBR | 21.0 MB | 2.75 Mbps | 138% | 9.9% | 0.9% | 34% / 20% |
| 정적 글자 / CBR | 60.0 MB | 7.86 Mbps | 172% | 11.5% | 2.2% | 36% / 24% |
| 고움직임 / VBR | 61.1 MB | 7.93 Mbps | 126% | 37.1% | 2.3% | 38% / 15% |
| 고움직임 / CBR | 60.3 MB | 7.93 Mbps | 142% | 53.4% | 2.4% | 37% / 15% |
| 고움직임 / VBR, 녹화 끔 | 없음 | — | 127% | 25.9% | 3.2% | 36% / 15% |

(CPU는 한 코어 기준 %, 메모리: FFmpeg 약 200 MB, FrameConsole 45~84 MB, MediaMTX 38~48 MB.)
- **재인코딩 없는 녹화의 부하 절감**: 녹화를 켜도 MediaMTX CPU는 한 코어의 1~3% 수준이고(녹화 끔 3.2% vs 켬 2.3%, 측정 오차 범위), 추가 인코더가 없습니다. 같은 영상을 따로 인코딩해 녹화했다면 FFmpeg 인코딩(한 코어의 약 130%와 GPU 인코더)이 한 번 더 들어갑니다. 낮은 재생 화질은 녹화하지 않아 중복 보관이 없습니다.
- **비트레이트 방식의 용량 절감**: 정적 글자 화면에서 VBR은 CBR의 35% 크기(65% 절감). 화질은 같습니다: 두 녹화의 같은 시점 키프레임은 디코딩 결과가 픽셀 단위로 동일했고, 5초 구간 전체 비교는 PSNR 46.8 dB·SSIM 0.995. CBR 파일에는 10초에 채움 데이터(Filler NAL) 314개가 들어 있어 추가 용량은 화질이 아니라 채움입니다. 확대 비교 `verification/storage/static-vbr-vs-cbr-crop.png`.
- 움직임이 많은 화면은 두 방식 모두 상한에 붙어 차이가 없습니다(상한이 화질을 정함).
- 정적 화면 VBR 2.75 Mbps의 대부분은 1초마다 넣는 키프레임 비용입니다. 키프레임 간격을 늘리면 줄지만 새 시청자 시작·탐색·화질 전환이 늦어져 바꾸지 않았습니다.
- 파일 분할이나 압축으로 영상 용량이 줄지는 않습니다(측정하지 않았고 주장하지 않음).

### 채팅 (`tools/test-chat.mjs`, 이전 단계 `smoke-v05.mjs`)
- 송출자(앱) ↔ LAN 수신자(Edge) 양방향 전송, HTML은 글자로 표시(`<img onerror>` 그대로 문자).
- 다른 방송 ID로 접속 → 거부·종료. 이름: 앞뒤·연속 공백 정리, 0자·21자·제어문자·폭 없는 문자·예약어(Admin) 거부, 20자 허용. 같은 PC의 송출 채팅과 수신 채팅은 같은 이름 허용(이전에는 "이미 사용 중"으로 막힘, 수정).
- 메시지: 1000자 허용, 1001자·빈 메시지·제어문자 거부, 10초 8개 제한(12개 연속 중 6개 거부), 늦게 들어온 사람에게 최근 기록 8개 전달.

- **다른 PC 간 같은 이름 거부는 다른 PC가 없어 시험하지 못했습니다**(이 PC의 모든 연결은 같은 PC로 판정).

### 송출 중 절전 방지
송출 중에는 Windows 전원 요청(시스템·화면 유지)을 걸고 종료 시 해제합니다. 확인 명령 `powercfg /requests`는 관리자 권한이 필요해 실행하지 못했습니다. 26분 부분 실행 동안 PC가 잠들지 않았고 녹화 빈 구간이 없었습니다(3시간 실행은 생략).

### 출력 규격과 여백 (같은 시험)
- 모든 경우 출력은 1920×1080 그대로였고, 내용은 원본 비율로 가운데 배치되었습니다. 미리보기(1280×720)와 수신 영상(1920×1080)의 여백 비율이 같았습니다(예: 정사각형 창 285/1280 = 425/1920, 세로 창 471/1280 = 705/1920).
- 여백의 원인 구분: 이전 영상의 위쪽 띠는 제목 표시줄(캡처 단계, 이번에 제거), 좌우 띠는 원본 비율이 출력과 다른 데서 생기는 필요한 여백(인코더 한 곳에서만 추가), 플레이어 안의 위아래 띠는 플레이어 틀(예: 채팅 열림 884×862)과 16:9 영상의 비율 차이(표시 단계, contain). 원본과 출력 비율이 같으면 여백이 없고, 짝수 반올림으로 생길 수 있는 1~2px 검은 줄은 없앴습니다.
- 플레이어 바깥 틀은 창 모양·화질·제목 표시줄 제거와 관계없이 그대로였습니다(모든 시험에서 863×772 / 884×862, 레이아웃 기준대로). 바깥 틀 고정·원본 비율·전체 내용 보존을 함께 지키면 비율이 다른 경우 여백을 모두 없앨 수는 없습니다.
- 수신 영상의 내용 경계 1px은 H.264 색차 표본화로 여백 검정과 섞여 보입니다(인코딩 특성, 내용 손실 아님).

## 장시간 DVR

3시간 시험은 사용자 요청으로 생략했습니다. 이전 빌드(추가 지시 반영 전)로 26분 연속 실행한 기록이 `verification/long-dvr-prev-build-partial.jsonl`에 있습니다: 녹화 구간 끊김 없음(20.4분 시점 한 구간, 60초 파일 21개), 녹화 약 3.4 MB/분, 프로세스 메모리 안정(FFmpeg 약 340 MB, FrameConsole 330 MB, MediaMTX 75~84 MB), 수신자 WebRTC 재생 유지. 이 실행에서 "시작 후 10분 지점" 이동은 하지 못했습니다(30분 시점 예정이었음). 짧은 시험(수 분)에서는 시작 부분·분할 경계·끝 부분 이동을 검증했습니다(위 DVR 표). **3시간 이상 연속 송출과 장시간 뒤 되감기는 미검증입니다.**

## 높은 FPS

0.5에서 다시 측정하지 않았습니다(빠른 진행 요청). 캡처·인코딩 파이프라인은 0.4와 같으므로 0.4 측정(`REPORT-v0.4.md`)이 기준입니다: 1080p 144 설정 시 송출 약 133 fps, 165 설정 시 약 128~131 fps, 2160p 60 설정 시 약 35 fps(원시 프레임 파이프 포화), 새 화면은 60 Hz 모니터라 초당 약 60장. 144/165 fps는 달성하지 못했습니다. 0.5에서 출력 크기가 선택 해상도로 고정되어 1080p 기준 픽셀 수가 약 6% 늘었으므로 상한은 0.4보다 조금 낮을 수 있습니다(미측정).

## 고FPS 캡처 대안 조사 (적용하지 않음)
FFmpeg 9.0.2의 `gfxcapture`(Windows Graphics Capture) → `h264_nvenc` 직결은 프레임을 GPU에서 넘겨 CPU가 한 코어의 11%(현재 파이프 방식은 130% 내외)였고, 1080p 165 fps·4K 120 fps를 실시간으로 처리했습니다(새 화면은 60 Hz 모니터 한계로 초당 60장, 나머지는 반복). 그러나 정지한 창·최소화된 창에서는 프레임이 전혀 나오지 않아 FFmpeg가 멈추고, 음성 동기화를 새로 설계해야 하며(시험 시 약 55 ms 어긋남), 크기 조절은 gfxcapture 자체 옵션만 동작하고 색 공간 표시가 BT.601로 기록되는 문제가 있어 이번 버전에는 적용하지 않았습니다.

| iPhone/iPad Safari | 미검증. MediaSource가 없으면 DVR을 숨기는 코드만 있음. |
| 모니터 연결 해제 중 송출 | 실제로 모니터를 분리해 보지 않았습니다. |
| QSV/AMF 실제 송출, 인코더 대체 | NVENC로만 송출 검증. 대체 경로의 결함은 코드 검토로 고쳤으나 실제로 NVENC 실패를 일으켜 보지 않았습니다. |
| Windows 10, WebView2 미설치 PC, 인터넷 없는 깨끗한 PC | 미검증(0.4와 같음). |
| 전원 요청 확인 | `powercfg /requests`(관리자 필요) 미실행. |

## 다른 PC 수신 재검증 절차

1. 송출 PC에서 관리자 PowerShell로 `dist\FrameConsole\tools\firewall-rules.ps1 -Profile Any -RemoveBlockRules` 실행(내용 확인 후). 허용 규칙: TCP 8889, UDP 8899(FrameConsole.exe), UDP/TCP 8189(mediamtx.exe).
2. FrameConsole.exe에서 송출 시작.
3. 다른 PC: FrameConsole.exe의 "전체 수신 목록"에 카드가 나타나는지(같은 서브넷), 또는 Chrome/Edge로 `http://192.168.1.27:8889/` 접속.
4. 카드 클릭 → 재생, 재생바로 처음 부분 이동, "실시간" 복귀, 이름 설정, 채팅 양방향.
5. 송출 PC 이벤트 기록에 `수신 | 시청 연결: <다른 PC IP> screen-01`이 보이면 다른 PC 수신이 확인된 것입니다(`data\logs\frame-console-*.log`에도 기록).
