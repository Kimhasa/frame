# 계정·채널·팔로우 실제 연결

2026-11-11 KST. 기존 React 화면과 Spring Boot에 PostgreSQL·Redis 연결을 추가하고 이 PC의 실제 앱 주소에 적용했다. 웹 회원은 미리 만들지 않았으며, 검증 계정은 별도 검증 DB에서만 생성했다. 커밋·푸시·배포는 하지 않았다.

## 실제로 연결한 흐름

- 이메일·비밀번호 회원가입 → 계정과 내 채널을 한 트랜잭션으로 생성 → 로그인
- 필수 이용약관·개인정보 수집·이용 동의 → 서버 문서 버전 검증 → 동의 버전과 서버 시각 저장
- 로그인·로그아웃·로그인 상태 유지, 서버가 확인하는 세션과 CSRF 토큰
- 프로필 이름과 채널 이름·소개·공지·카테고리·배너 프리셋 저장
- 공개 채널 조회·검색, 팔로우·해제·방송 알림 선호 설정과 실제 팔로워 수
- 로그인 없이 팔로우 → 로그인 화면 → 로그인 후 원래 채널로 복귀
- 기존 OBS 스트림 키로 소유권 확인 → 내 채널과 송출 경로 연결 → 소유자만 스튜디오·송출 정보 조회

PostgreSQL은 계정·채널·팔로우와 송출 경로 연결을 저장한다. Redis는 Spring Session 로그인 상태와 만료를 저장한다. JWT·별도 인증 서버·이벤트 버스는 추가하지 않았다. 비밀번호는 PBKDF2로 해시한다. 쿠키는 HttpOnly·SameSite=Lax이며 HTTPS 운영 설정은 Secure를 요구한다.

일반 개발·프로덕션 화면은 실제 제품 API를 사용한다. `build:design`과 기존 포트폴리오 번들은 별도의 시안 데이터를 유지한다. 회원에게 기존 로컬 운영자 Bearer를 자동 주입하지 않으며, 채널 소유권 확인 없이 송출 키나 공용 결제 내역을 반환하지 않는다.

## 실행과 시작 위치

- 앱 회원가입: `http://127.0.0.1:5360/_frame/login?mode=register`
- PostgreSQL 17.11: `127.0.0.1:15432`, 실제 DB `frame_product`, 검증 DB `frame_product_verify`
- Redis 8.10.3: `127.0.0.1:16379`, 인증 필수, 실제 세션 namespace `frame:product:sessions`
- 설정: 저장소 밖 `%LOCALAPPDATA%/Frame/product/config.json`

```powershell
node server/product-local.mjs start
node server/obs-local.mjs start
yarn --cwd apps/web dev --port 5360
```

이미 송출 서버가 실행 중일 때 API만 교체하려면 `node server/obs-local.mjs restart-api`를 사용한다. 이 명령은 MediaMTX와 OBS 입력을 유지하며 Spring만 교체한다. 실행용 JAR을 저장소 밖 버전별 사본으로 만들어, 이후 빌드가 실행 중 JVM의 파일을 교체하지 않게 했다.

기존 PostgreSQL 5432 서비스·계정·DB는 변경하지 않았다. 이 PC의 Redis는 SHA-256을 확인한 Windows 커뮤니티 포터블 빌드이며 버전·원본·실행 방식은 [로컬 환경 문서](../../deploy/PRODUCT_LOCAL.md)에 기록했다.

가입한 뒤 방송 스튜디오에서 **기존 OBS 송출 연결**에 OBS에 설정된 스트림 키 전체를 입력하면 된다. 첫 가입자에게 기존 경로를 자동 귀속시키지 않는다. DB에는 연결한 경로만 저장하고, 증명에 사용한 송출 키는 저장하지 않는다.

## 찾아 고친 장애 격리

초기 검사에서는 Spring Session 필터가 모든 URL에 적용되어, Redis 연결 불가 시 로그인 쿠키를 가진 공개 미디어 요청도 실패했다. 필터를 `/api/v1/*`에만 적용하고 계정 API의 Redis 장애는 `503 PRODUCT_UNAVAILABLE`로 응답하게 했다.

실제 Redis를 중지하지 않고 별도 검증 API에 연결 불가한 Redis 포트를 지정했다. 정상 서버에서 인증되는 동일 쿠키를 사용했을 때 계정·팔로우·스튜디오는 503으로 거절됐고, 공개 방송 목록과 상태는 200을 유지했다. 익명 세션도 가짜 200이나 CSRF 토큰을 만들지 않았다. [수정 전 재현](redis-failure-before-fix.json), [수정 후 독립 검사](redis-failure-result.json)

## 로그인·회원가입 컴포넌트 정리

2026-11-11. 로그인·회원가입의 일반 소개 문구와 대화형 하단 링크를 제거했다. 회원가입 제목은 가운데 정렬하고, 로그인 하단은 `회원가입 / ID 찾기 / 비밀번호 찾기`, 가입 하단은 `로그인 / ID 찾기 / 비밀번호 찾기`로 맞췄다. ID 안내는 가입 이메일을 설명하며 비밀번호 복구는 미연결 상태를 알린다. 실제 복구 메일을 보낸 것처럼 표시하지 않는다.

공유 `AuthCheckbox`는 같은 녹색·22px 컨트롤을 사용한다. 기본 체크, 일부 동의, 미동의 오류, 비활성, hover, Space 조작과 키보드 focus를 확인했다. 회원가입에는 필수 동의 두 항목과 전체 동의, 문서 상세 dialog를 추가했다. 약관을 읽거나 닫는 동작은 동의를 대신하지 않는다. dialog는 Escape·바깥 클릭으로 닫히며 호출 버튼으로 focus를 돌린다.

`server/verify/auth-ui.mjs`는 별도 검증 DB와 5364 화면에서만 가입한다. 실제 서버 문서를 사용하되 약관 조회 503, 구버전 응답, 지연된 가입 요청은 CDP로 주입해 실패 상태와 재시도를 검증했다. 조회 실패 시 가입 차단, 버전 변경 시 문서 재조회·동의 초기화·입력값 유지, 재동의 후 안내 해제, 처리 중 입력·화면 전환 잠금, 실제 가입·새로고침 후 인증 유지, 390px·320px 가로 넘침을 확인했다. 현재 실제 주소 5360에서는 새 회원을 만들지 않고 빈 가입 화면과 개발 StrictMode의 dialog 유지·복귀만 확인했다.

V2 migration은 기존 계정의 동의 정보를 `NULL`로 보존하며 소급 동의로 기록하지 않는다. API만 새 JAR로 적용했고 MediaMTX 수신 프로세스는 유지했다. 문안은 현재 기능에 맞춘 초안이며 정식 공개 전 운영 주체·문의 경로, 탈퇴·삭제·동의 철회 절차를 확정해야 한다. 수집·이용 고지 항목은 [개인정보 보호법 제15조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1029334879)를 참고했으며 법률 검토 완료를 의미하지 않는다.

## 가입 입력 간소화·공개 약관 조회 보완

2026-11-11. 가입 폼의 채널 ID 입력과 설명을 제거했다. 서버가 `ch-`와 임의 80비트 hex로 주소를 발급하며, PostgreSQL 고유 제약 충돌 시 새 후보를 최대 5번 시도한다. 이메일·닉네임을 주소에 넣지 않으며 기존 채널 주소는 유지한다. 명시적 handle을 보내던 API 호출은 호환된다. 실제 PG 검사에서는 자동 생성·고유성·명시 주소 보존·충돌 재시도·트랜잭션 롤백·동의 저장을 확인했다.

약관 영역의 바깥 박스와 두 겹의 div를 제거해 체크 항목을 폼에 직접 배치했다. 로고 아래 간격은 로그인 46px, 회원가입 제목 앞 30px로 넓혔다. 하단 링크는 14px·650 굵기로 맞추고 구분선 pseudo-element를 제거했다.

사용자가 본 약관의 `로그인이 필요해요` 응답은 현재 실제 서버에서 직접 재현되지 않았다. 18080·5360의 익명·형식이 잘못된 쿠키·Redis에 없는 세션 쿠키 12조합 모두 공개 약관과 익명 session을 200으로 반환했다. 기존 IAB 탭에 남아 있던 계정 조회 오류는 재시도 후 200으로 회복했고, 같은 브라우저에서 비로그인 약관 조회·상세 열람도 200으로 확인했다. 정책 요청은 명시적으로 `credentials: omit`으로 분리했으며, 정책 조회에서 401이 오더라도 가입자에게 로그인을 요구하는 문구를 표시하지 않는다. 오류를 가짜 문서나 동의 성공으로 바꾸지는 않는다.

별도로 재현된 두 복구 결함을 보완했다. DB에 없는 계정을 가리키는 Redis 인증 세션은 `/session`의 첫 401에서 폐기해 다음 GET이 익명 CSRF를 만들게 했다. 정상 세션과 503에서는 인증 정보를 지우지 않는다. 가입·로그인 중 CSRF가 만료되면 새 session을 조회하고 입력·동의 상태를 유지한다. 가입 POST는 자동 재전송하지 않으며 사용자가 다시 눌러 진행한다.

갱신된 `auth-ui.mjs` 35개 검사는 공개 약관 401·503, 계정 쿠키 미전송, 굵은 링크·구분선 제거, ID 입력·약관 박스 제거, 실제 만료 쿠키 복구, 자동 주소가 있는 계정 가입·새로고침까지 확인했다. 실제 주소에서는 빈 화면과 공개 문서만 확인했으며 사용자 DB에 검증 계정을 만들지 않았다.

## Docker 개발 환경·Flyway 검증 보강

2026-11-12. 기존 구현에는 Flyway V1·V2가 연결돼 있었으며 실제 사용자 DB의 `flyway_schema_history`만 읽기 전용으로 확인해 모두 성공 상태임을 확인했다. 기존 SQL은 변경하지 않았다. `validate-on-migrate: true`, `clean-disabled: true`, `baseline-on-migrate: false`를 명시하고 검증 DB의 임의 schema에서 빈 DB 적용·재실행 0건·V1 데이터 보존 업그레이드·임시 SQL 변조 시 checksum 실패와 신규 DDL 차단을 검사했다. 제품 기능을 끄면 DB·Redis·Flyway 없이 기존 미디어 API가 부팅되는 검사도 포함한다.

## 방송 예약 실제 저장·공개 일정 연결

2026-11-12. 재부팅을 미루고 기존 PC의 PostgreSQL·Redis 환경에서 구현·검증했다. Flyway V3 `product_broadcast_schedules`를 추가하고 본인 예약 조회·추가·수정·취소와 공개 채널의 미래 일정 조회를 연결했다. 기존 V1·V2 SQL은 변경하지 않았다. 소유 채널은 세션에서 결정하며 다른 계정의 수정·취소는 404다. 같은 채널의 중복 시작 시각은 DB 고유 제약으로 거절한다. 지난 예약은 이력으로 남고 수정·취소할 수 없다. 미래 예약은 100개 상한이며 채널 행 잠금으로 동시 생성의 상한 초과를 방지한다.

예약 시각은 epoch milliseconds로 저장하고 화면은 서울 시간으로 입력·표시한다. 제목은 Unicode 1~100자, 현재 이후의 유효 정수 시각만 받는다. 본인 목록은 가까운 미래 100건과 최근 과거 100건이다. 공개 조회에는 미래 일정의 id·제목·시각만 반환한다.

기존 예약 화면의 색감·레이아웃을 유지했다. 저장 성공 응답 뒤에만 목록과 완료 안내를 바꾸고, 저장·취소 실패 때는 입력과 확인 창을 유지한다. 처리 중 중복 제출·Escape·닫기를 막고 완료 뒤 포커스를 복귀한다. 실제 화면의 `?state=empty`로 저장된 예약을 숨길 수 없다. 공개 일정의 조회 실패도 빈 일정으로 표시하지 않고 재시도를 제공한다. React 디자인 번들은 기존 시안 동작을 유지하며 배포 번들에는 예약 시안 데이터를 포함하지 않는다.

검증 계정·예약은 별도 검증 DB에서만 생성했다. 실제 HTTP 24/24, headless Edge 브라우저 23/23, API 재시작 후 보존 3/3을 통과했다. 데스크톱·390px 화면을 직접 확인했으며 런타임 오류는 0건이었다. 정상 CRUD 외에 서버 503·중복 충돌·지연 응답, 인증·CSRF·Origin·타인 예약 차단을 확인했다. backend 전체 73/73 이후 상한·동시 생성 보완에 관련 집중 검사 5/5와 최종 JAR 빌드를 다시 수행했다.

실제 API는 MediaMTX 입력을 유지하며 새 JAR로 교체했다. 사용자 DB에는 V3 테이블만 추가했고 시험 회원·예약을 넣지 않았다. 이 기능은 방송 일정 관리이며 OBS 자동 시작·푸시 알림 전송은 포함하지 않는다. Docker 엔진·컨테이너 검증은 재부팅 뒤에 진행한다.

## 시청 기록 실제 저장·조회 연결

2026-11-12. 기존 녹색·여백·시청 기록 레이아웃을 유지하며 로그인한 사용자의 라이브 시청 기록을 PostgreSQL에 연결했다. 페이지 진입이나 방송 목록 조회만으로 저장하지 않는다. 현재 방송과 일치하는 플레이어에서 재생 가능한 영상이 실제로 1초 이상 진행된 뒤 저장한다. 일시정지·신호 대기·탐색으로 건너뛴 시간은 재생 근거로 쓰지 않는다. 디자인 전용 화면에는 저장 연결을 넣지 않았다.

한 시청 방문에서 저장 성공은 한 번이다. 다른 창에서 기록을 삭제한 뒤 현재 재생을 계속해도 heartbeat로 기록이 다시 생기지 않는다. 방송을 나갔다가 다시 들어와 실제로 재생하면 새 시청으로 저장한다. 같은 방송 재시청은 마지막 시청 시각을 갱신한다. 일시적인 저장 오류는 실제 재생이 계속되는 동안에만 5초·15초 간격으로 최대 두 번 재시도하며, 기록 API 오류가 영상 재생 상태를 바꾸지 않는다.

`/api/v1/me/history`는 인증된 본인의 저장·조회·개별/선택/전체 삭제만 제공한다. 서버의 현재 방송에서 제목·방송자와 시각을 가져오며 클라이언트가 보낸 사용자·제목·시각을 신뢰하지 않는다. 제목·방송자 검색, 서울 날짜 기준 기간 필터, 마지막 시청 순서의 커서 페이지 이동을 지원한다. 선택 삭제는 최대 200개이며 누락·타인 ID가 섞이면 전체 삭제를 거절한다. 검색된 일부 기록만 화면에 있더라도 전체 삭제는 본인 전체 기록에 적용한다.

Flyway V4에 기록 테이블·외래 키·조회 인덱스를 추가했다. 기존 V1~V3 SQL은 보존했다. 기록의 방송 ID·경로와 내부 방송 instance UUID를 함께 비교하므로 종료된 ID·경로를 다시 사용하거나 API가 재시작돼도 이전 기록을 다른 방송의 링크로 바꾸지 않는다. 종료 후에도 제목·방송자·시청 시각은 보존하고 화면에는 `방송 종료`로 표시한다. 현재 실제 기록 대상은 라이브이며 다시보기·클립의 자동 기록은 아직 연결하지 않았다.

화면은 서버의 조회 실패와 빈 목록을 구분하고 재시도를 제공한다. 더 보기 실패는 이미 불러온 항목을 유지한다. 삭제는 서버 성공 후에만 반영하며 실패 시 목록·선택·확인 창을 유지한다. 처리 중 중복 제출·닫기·Escape를 막고 공통 커스텀 체크박스와 포커스 복귀를 사용한다. 실제 화면에는 시안 데이터·sessionStorage 기록·가짜 실행 취소를 넣지 않았다.

별도 PostgreSQL 검증 DB·Redis namespace에서 백엔드 전체 79/79, 실제 HLS 재생 및 저장 검사 15/15, 화면 검사 23/23을 통과했다. 재생 검사는 별도 MediaMTX·FFmpeg(320×180, 15fps, H.264/AAC)·Spring·배포 React·headless Edge로 수행했고 기존 OBS 수신 경로에 송출하지 않았다. 최초 저장 503 중 영상 진행과 지연 재시도, 신호 대기 중 미저장, 중복 쓰기 방지, 재생 중 삭제 뒤 미복원, 재방문 저장, 브라우저 새로고침·API 재시작 후 기록과 로그인 보존을 확인했다. WHEP 요청과 브라우저 런타임 오류는 0건이었다. `history-e2e-result.json`의 16번째 검사는 아래 UI 23개 검사의 통과 여부를 집계한 항목이다.

페이지 이동·검색·삭제 UI 검사는 별도로 명시적으로 등록한 53개 메타데이터 기록을 사용했다. 첫 50개와 다음 3개, 첫 페이지 밖의 검색, 종료 행, 개별·선택 삭제 503, 지연된 전체 삭제와 실패 재시도, 불러오지 않은 기록까지 삭제, 390px 선택 상태를 확인했다. 이 53개는 재생 자동 기록의 증거로 사용하지 않았다. 데스크톱·모바일 캡처도 확인했다. 실행 명령은 API·웹 빌드 후 `node server/verify/history-e2e.mjs`이며 비밀은 저장소 밖 로컬 설정에서만 읽는다.

검증 뒤 실제 API를 새 JAR로 교체하고 V4 적용 성공을 읽기 전용으로 확인했다. 실제 사용자 DB에는 시험 회원·시청 기록을 넣지 않았다. MediaMTX 수신 프로세스를 유지했고 로컬 웹은 `http://127.0.0.1:5360/_frame/history`에서 실행 중이다. `/healthz`·공개 약관 200, 비로그인 개인 기록 조회 401을 확인했다. 재부팅·Docker 엔진 기동·커밋·푸시는 수행하지 않았다. 휴대폰 실기기·Caddy HTTPS/WSS·인터넷·수용량 검증은 이번 범위에 포함하지 않는다.

## 채널 상세·프로필 링크·핸들 변경·신고 접수

2026-11-12. 기존 녹색과 채널·스튜디오 레이아웃을 유지하며 공개 채널에 소개 요약·`더보기`, 첫 외부 링크와 나머지 링크 목록, 채널 공유를 추가했다. 상세 dialog는 전체 소개·정렬된 링크·국가·채널 생성일·실제 팔로워 수를 보여 준다. 채널 생성일은 기존 `product_channels.created_at`을 사용하며 계정 가입일로 대체하거나 새로 만들어 채우지 않는다. 링크는 HTTP(S) 주소만 렌더하고 새 창은 `noopener noreferrer`를 사용한다. 정보 행에는 읽기 쉬운 `@핸들`을 표시하고, 복사·Web Share에는 핸들 변경에 영향을 받지 않는 UUID 주소를 사용한다.

채널 관리에서 이름·소개·공지·카테고리·배너와 함께 핸들·선택 국가·외부 링크를 실제 저장한다. 링크는 제목/URL의 순서를 유지하는 최대 14개이며 추가·삭제·위/아래 이동을 제공한다. 제목은 Unicode 1~50자, URL은 최대 500자, JSON 본문은 전체 8KB다. 화면에서도 UTF-8 바이트 수를 검사한다. 위험한 스킴·주소 내 자격 증명·제어 문자·내부 공백은 거절하며 입력은 유지한다. 핸들은 선택적인 `@` 하나를 제외하고 소문자로 정규화한 기존 3~24자 영문·숫자·밑줄·하이픈 규칙을 유지한다. `@@` 입력을 여러 이벤트에서 반복 정규화해 유효한 값으로 바꾸지 않는다.

내부 채널 UUID와 팔로우·예약·기록의 참조는 그대로다. Flyway V5는 기존 채널의 현재 핸들을 단일 주소 예약 테이블에 백필한다. 현재·과거 핸들은 같은 고유 제약으로 선점하므로 등록과 변경이 동시에 실행돼도 다른 채널이 같은 이름을 가져가지 않는다. 이전 이름은 원래 채널에 계속 연결되고 본인이 다시 사용할 수 있으며, 채널 삭제 후에는 tombstone으로 예약을 남긴다. 이 버전은 과거 이름을 기간 만료 후 다른 사람에게 재배정하지 않는다. 기존 `/channel/{handle}`와 새 `/channel/id/{uuid}`가 같은 채널을 열고, 공개 화면은 현재 핸들로 주소를 정리하면서 탭·fragment를 보존한다.

채널 신고는 로그인한 다른 사용자가 사유·선택 상세 내용을 작성해 실제 DB에 접수하는 범위다. `기타` 사유에는 내용을 요구한다. 요청이 201로 완료된 뒤에만 접수 화면으로 바꾸며 실패 시 사유·내용을 유지한다. 자기 채널 신고는 허용하지 않는다. 같은 신고자·대상·사유는 24시간 내 중복 접수를 409로 거절하고, 사용자당 최근 1분 최대 5건을 트랜잭션에서 보장한다. 비로그인 신고는 현재 채널로 돌아올 경로를 보존해 로그인으로 이동하며 팔로우를 자동 실행하지 않는다. 신고자·내용은 공개 프로필에 반환하지 않는다. 관리자 검토·조치 API/화면은 이번에 구현하지 않았고 접수를 검토 완료로 표시하지 않는다.

영상 수·누적 조회수는 아직 실제 영상 카탈로그와 조회 집계가 없어 API에서 `null`로 반환하고 화면에서 생략한다. 개인 시청 기록이나 DVR 파일 수로 대체하지 않는다. 실제 0명인 팔로워 수는 그대로 표시한다. 제품 API·화면 계약은 [PRODUCT_API.md](../../apps/api/PRODUCT_API.md)에 기록했다. V1~V4 SQL은 변경하지 않았다.

실제 PostgreSQL·Redis를 포함한 backend `test bootJar` 86/86, 배포 React의 브라우저 검사 33/33, Vite 개발 StrictMode 검사 6/6을 통과했다. 실제 프로필 저장·실패 보존·지연 요청 중 중복 제출 차단·재조회, 링크 정렬과 안전 URL, 이전 핸들/UUID 경로, 국가·생성일·미집계 항목 생략, 공개 상세·공유, 로그인 복귀·신고 503 보존·실제 201 접수·실제 중복 409, 390px·320px의 편집기/상세 창을 확인했다. 개발 검사에서는 dialog 포커스·Escape 복귀, 복사 권한 거절 때 수동 복사 선택, Web Share 취소와 작은 화면을 확인했다. 복사·Web Share는 브라우저 spy로 payload와 실패/취소 상태를 검사했으며 OS 공유 창이나 외부 메시지를 보내지 않았다. 브라우저 런타임 오류는 0건이었다.

## 플랫폼 운영자 신고 관리

2026-11-12. 접수된 채널 신고를 플랫폼 운영자가 조회·검토하는 실제 화면을 `/_frame/admin/reports`에 연결했다. 기존 스튜디오의 색감·여백·테이블·입력 스타일을 유지했다. 운영자는 프로필 메뉴 또는 사이드바의 `플랫폼 관리 → 신고 관리`에서 이동한다. 일반 크리에이터에게는 플랫폼 신고 메뉴를 표시하지 않고, 본인 채널에 대한 신고라도 관리자 목록·상세·수정 API를 허용하지 않는다. 이전 실제 `/studio/reports` 주소는 운영자에게 새 경로로 연결하고 일반 회원에게 권한 부족 화면을 제공한다. 디자인 모드의 기존 시안은 그대로 유지한다.

Flyway V6는 계정의 `is_operator`를 기본 `false`로 추가한다. 최초 가입자·특정 이메일·로그인 세션의 임의 ROLE을 근거로 자동 승격하지 않는다. session 응답에는 `user.isOperator`를 포함하고 관리자 API는 매 요청 DB 권한을 다시 확인한다. 기존 Redis 로그인 상태에서도 권한 회수 뒤의 다음 요청부터 403 `OPERATOR_REQUIRED`다. 화면도 해당 응답을 받으면 기존 목록·상세 창·메뉴를 지우고 세션을 다시 확인한다. 인증 만료는 비공개 데이터를 지운 뒤 현재 경로를 보존해 로그인으로 이동한다.

실제 신고 목록은 채널 이름·핸들·신고 내용의 검색, 사유·상태 필터, 접수 시각/UUID 내림차순 커서 조회를 지원한다. 목록·상세에는 채널/신고자의 ID·표시 이름만 필요한 범위로 반환하고 이메일·비밀번호·송출 자격 증명은 반환하지 않는다. 상세 창은 원문·사유·접수 시각과 검토 기록을 구분해 보여 준다. `접수 → 검토 중 → 검토 완료` 또는 기각을 저장할 수 있고 접수에서 바로 완료/기각도 가능하다. 검토 종료 시 1,000자 이내의 기록이 필수이며 처리자와 시각은 서버가 결정한다. 원래 신고 내용·신고자·접수 시각은 수정하지 않는다. 검토 완료·기각은 다시 수정하거나 되돌리지 않는다. 이 기능은 검토 상태와 기록 저장이며 채널 제한·삭제를 실행하지 않는다.

행 version을 사용해 동시 수정은 409 `REPORT_CONFLICT`로 거절한다. 화면은 입력을 유지하고 자동 재전송을 막으며 사용자가 `최신 내용으로 새로고침`을 선택해 최신 상태를 확인하도록 한다. 목록/상세 조회 실패는 빈 목록과 구분하고 재시도를 제공한다. 저장 503은 선택 상태·기록·상세 창을 유지한다. 저장 중 필드·닫기·Escape·중복 제출을 막고, 닫을 때 원래 버튼 또는 유효한 페이지 제목으로 포커스를 복귀한다.

## 실제 웹 알림·방송 시작·신고 결과

2026-11-12. 기존 녹색·알림 화면 폭·여백을 유지하며 `/_frame/notifications`를 계정별 PostgreSQL 알림에 연결했다. 알림을 켠 팔로우 채널의 실제 방송 시작과, 본인이 접수한 채널 신고의 최종 검토 결과를 저장한다. 실제 목록에는 시안 데이터·sessionStorage 읽음 상태를 쓰지 않는다. 전체/읽지 않음·방송 시작/신고 결과 필터, 날짜별 묶음·실제 시각, 더 보기, 읽음·전체 읽음, 개별/전체 삭제를 지원한다.

방송 시작은 공지나 목록 등록만으로 생성하지 않는다. fresh MediaMTX root 경로의 준비된 소스와 Registry의 실제 관측 소스가 일치한 뒤 제품 전용 5초 worker가 처리한다. 소스 세션(type·source ID·ready 시각)의 지문과 방송 instance의 두 영구 marker를 같은 트랜잭션에서 예약한다. source ID가 없는 호환 입력은 유효한 ready 시각과 type으로 지문을 만든다. 이미 알려진 소스를 API 재시작 후 관측해도 새 instance marker를 함께 남기므로 짧은 재연결까지 중복을 억제한다. 실제 새 소스와 새 방송 instance는 새 시작으로 처리할 수 있다. 알림 행을 삭제해도 marker는 유지한다.

Flyway V7은 채널의 기능 도입/송출 경로 연결 기준 시각과 팔로우의 알림 ON 시각을 저장한다. 기능 도입 때 이미 송출 중인 방송, 방송 중 늦은 채널 연결·팔로우·알림 ON은 과거 시작 알림으로 보내지 않는다. 기존 팔로우 선호는 보존하며 다음 실제 방송부터 적용한다. 알림 DB 작업은 미디어 scheduler·동기 Registry listener 밖의 전용 thread에서 실행한다. 트랜잭션·SQL·잠금 대기에 한도를 두고 실패는 다음 주기에 재시도한다. 영상·송출 처리에 DB 예외를 전파하지 않는다.

신고는 검토 완료/기각 저장과 일반 결과 알림을 같은 트랜잭션에서 커밋한다. 결과 알림은 공개 채널 이름·일반 안내·본인 신고 번호·최종 상태만 제공하며 운영자 이름·내부 검토 메모는 포함하지 않는다. 개인 결과 창에서 확인하며 관리자 화면으로 연결하지 않는다. 방송 알림의 재생 가능 여부는 저장한 방송 ID·경로·instance·소스 세션과 현재 fresh 상태를 모두 확인한다. 종료·API 재시작 후 이전 알림을 다른 방송 링크로 바꾸지 않고 고정 채널 UUID 경로로 연결한다.
