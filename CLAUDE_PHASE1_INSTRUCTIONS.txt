기존 데스크톱 레이아웃, Pretendard, 색상·간격·아이콘, 자체 선택 메뉴, 포커스·슬라이더, 카드와 모달 구성을 재사용한다. 프레임워크 이관이나 대시보드 재디자인을 하지 않는다.
허용 변경은 모바일 반응형 배치·터치 조작·자동 화질의 실제 상태 표시·사용자가 요청한 환경 문구 제거·접속에 필요한 최소 상태/오류 표시다. 기존 화질 메뉴의 자동/수동 선택을 재사용하고 불필요한 설명 카드·데모 표시·큰 제목·시작 버튼 옆 상태 배지를 추가하지 않는다.
데스크톱에서 상세 진입만으로 사이드바를 자동 축소하지 않는다. 기존 확대 보기에서만 축소하는 동작을 유지한다. 휴대폰 폭에서는 별도의 반응형 탐색 방식으로 공간을 확보하되 데스크톱 동작을 바꾸지 않는다.
캡처 창 크기나 재생 화질이 달라져도 플레이어 바깥 배치가 갑자기 바뀌면 안 된다. 원본 비율·전체 내용 보존, 제목 표시줄 제외, 영상 클릭 재생/정지와 터치 조작을 유지한다.
reference/, reference-v05/, UI_LOCK.json, UI_V05_LOCK.json, UI_V051_ADDENDUM.json은 그대로 보존한다. 현재 0.5.1 검사는 node tools/verify-ui-v051.mjs다. 모바일과 환경 문구 제거는 기존 정적 해시와 충돌하므로, 허용 차이를 별도 새 기준/검사로 기록하고 변경 전후 데스크톱·모바일 화면을 비교한다. 기존 해시를 덮어써 변경 없음을 꾸미거나 검사를 통째로 끄지 않는다.

1. 동시 시청 1,000명 목표와 부하 검증

기본 목표는 한 방송을 영상·음성과 함께 시청하는 1,000개 세션이다. 이 중 채팅 연결도 유지하는 기본 시청 흐름을 검증한다. 여러 방송을 합산한 1,000명, 같은 브라우저 탭 1,000개, 목록 API 요청 1,000개를 이 목표와 혼동하지 않는다.
비교 기준은 우선 1080p 60fps 원본 한 개와 실제 비트레이트다. 저화질 혼합 시청, 여러 화질 동시 생성, 여러 방송은 별도 시나리오로 측정한다. 144/165fps는 지원 장비에서 별도 검증하고 선택 목표와 실제 새 프레임·디코딩 FPS를 구분한다.
단계는 1 → 10 → 50 → 100 → 300 → 500 → 1,000명으로 설정 가능하게 만든다. 각 단계는 램프업 후 최소 5분 정상 구간을 측정하는 것을 기본안으로 둔다. 최종 통과 단계에서는 자원·트래픽 예산이 허용하면 30분 이상 지속 시험을 추가한다. 이 시간과 인원은 변경 가능한 시험 설정으로 관리한다.
동시 입장, 일정 속도 입장, 시청자 교체·재접속, 모바일/PC 혼합, 채팅·DVR·화질 변경을 함께 쓰는 조건을 포함한다. 1,000명이 채팅방에 연결된 경우와 실제 메시지를 보내는 비율·빈도는 구분해 기록한다.
부하 발생기는 실제 미디어를 받는 WebRTC peer 또는 HLS 재생 클라이언트여야 한다. HTTP 200, WHEP 협상 성공, 탭이 열렸다는 사실만으로 시청 성공으로 세지 않는다. 첫 미디어 수신과 이후 지속 수신을 확인한다.
전체 프로토콜 부하는 가벼운 클라이언트로 만들 수 있지만 영상 디코딩·화면 렌더링·오디오 동기화·재버퍼링은 대표 실제 브라우저에서 별도로 검증한다. 브라우저/프로토콜 클라이언트, 디코딩 여부, 실행 위치, 네트워크와 시청자 수의 정의를 보고서에 명시한다.
송출기·중계 서버·부하 발생기의 CPU/RAM/GPU/네트워크를 모두 수집한다. 가능하면 다른 장비와 여러 부하 발생기로 나눠서 시험한다. 한 PC의 생성기 CPU나 네트워크가 먼저 포화되면 서버 한계로 결론 내리지 않는다. 루프백/사설망 시험을 인터넷 1,000명 검증으로 보고하지 않는다.
세션 수, 재생 시작 성공률, 첫 프레임 시간(p50/p95), 재버퍼 횟수·시간 비율, 프레임 드롭·실제 FPS, 라이브 지연, 패킷 손실, CPU/RAM/GPU 인코더, 서버 송신량, 송출 PC 업로드, 채팅 전달 시간과 실패, DVR 오류율을 기록한다. 프로토콜에서 측정할 수 없는 지표를 0으로 채우지 말고 미측정으로 표시한다.
라이브 지연은 단말 간 시계가 맞거나 영상 내 타임코드 등 신뢰할 수 있는 기준으로 측정한다. getStats의 jitter buffer 지연을 전체 캡처→화면 지연으로 보고하지 않는다. 재버퍼링은 사용자의 일시정지·탐색과 구분한다.
초기 잠정 기준: 정상 네트워크에서 재생 시작 성공률 99% 이상, WebRTC 첫 프레임 p95 5초 이내, HLS 계열은 p95 10초 이내, 정상 재생 중 재버퍼 시간 비율 1% 미만을 목표로 한다. 이는 확정 SLA나 현재 측정값이 아니다. 프로토콜·인코더 예열·모바일 조건을 명시하고 사용자 체감 지연도 별도로 보고한다. 장시간 단절 조건에 이 정상망 기준을 억지로 적용하지 않는다.
포화·강제 종료·지속 메모리 증가·세션 정리 실패를 확인한다. 상한 초과 때는 무한 대기·프로세스 종료 대신 정해진 대기/재시도/수용 제한으로 처리한다. 상한과 스레드만 무작정 늘리는 변경은 피한다.
8Mbps × 1,000명은 영상 데이터만 약 8Gbps, 1시간 약 3.6TB 송신이다(오버헤드·중계 홉 제외). 혼합 화질의 실제 평균과 CDN·TURN의 각 구간을 따로 산정한다. 1,000명은 아키텍처상 가능한 목표지만 현 PC·무료 서버에서 달성한다고 보장하지 않는다.
현재 예산은 무료 시험이다. 무료 서비스의 용량·트래픽 한도와 영상 전송 허용 범위를 먼저 확인한다. 임의 유료 자원 생성·자동 업그레이드·유료 트래픽 사용을 하지 않는다. 시험 시간·최대 송신량·중단 조건을 설정하고 지원 환경이 없으면 스크립트와 재현 절차를 남기며 해당 단계는 미검증으로 보고한다. 작은 인원 결과를 선형 외삽해 1,000명 통과로 바꾸지 않는다.

2. 시청자별 네트워크 자동 재생 화질

시청자의 자동 선택이 실제 인코딩된 서로 다른 화질 스트림을 고르게 한다. 화질 표시 숫자, CSS 크기, 원본 한 스트림의 비트레이트만 바꾸는 것으로 완료하지 않는다.
우선 원본 범위 안의 360p/480p/720p/1080p 등 설명 가능한 화질 단계를 만들고, 실제 장면·FPS·코덱 기준으로 비트레이트를 측정해 조정한다. 원본보다 큰 가짜 화질을 만들지 않는다. 화질별 해상도·FPS·코덱·대역폭 정보를 제공한다.
동일 화질은 시청자들이 공유한다. 한 시청자나 전환 요청마다 FFmpeg 인코더를 새로 만들지 않는다. 화질 스트림 최초 기동, 대기·실패·유휴 종료와 요청 몰림을 처리한다.
자동 모드에서는 수신 상태·버퍼·재버퍼링·손실·디코딩 부하·플레이어 크기 등 이용 가능한 신호를 함께 본다. WebRTC getStats의 지원 차이와 누락을 처리한다. 현재 스트림의 실제 수신 비트레이트는 가용 회선 속도 그 자체가 아니다. 네트워크 API 값 하나만 믿지 않는다.
화질 하향은 끊김을 줄일 만큼 빠르게, 상향은 충분한 여유가 지속될 때 보수적으로 한다. 안전 여유·관찰 창·상하향 조건·최소 유지 시간·실패 복구를 설정값으로 관리하고 바뀐 이유를 로그에 기록한다. 경계 속도에서 화질이 계속 왕복하지 않게 한다.
한 시청자의 회선이 느려져도 원본 송출이나 다른 시청자의 화질을 일괄 낮추지 않는다. CPU 디코딩 한계와 네트워크 한계도 가능한 범위에서 구분한다.
수동 화질은 사용자가 바꾸거나 자동을 다시 선택하기 전까지 유지한다. 실제 재생 불가인 경우 기존 오류 방식으로 설명하고, 자동으로 돌아간 것처럼 조용히 덮어쓰지 않는다. 자동 메뉴에는 현재 실제 재생 화질이 맞게 표시되어야 한다.
전환 시 검은 화면·화면 크기 변화·오디오 겹침·중복 peer/인코더·이전 연결 누수를 막는다. 첫 프레임/키프레임·세그먼트 준비 후 교체하고 실패하면 직전 재생을 보존하거나 명확히 복구한다.
라이브·DVR·일시정지·실시간 복귀를 구분한다. DVR에서 자동 화질이 무엇을 의미하는지 명시하고 아직 원본 녹화만 있으면 가짜 다중 화질을 표시하지 않는다. 수동 품질 변경이 탐색 위치나 실시간/과거 모드를 임의로 바꾸면 안 된다.
대역폭 15→8→3→1→0.5→8→15Mbps 등 단계 변화, 왕복 지연·손실·지터, 순간 끊김과 복구를 재현한다. 예시는 시험 프로필이며 단말별 실제 제한을 기록한다. DevTools의 HTTP 제한이 WebRTC UDP까지 제한한다고 가정하지 말고 실제 미디어 경로에 제한이 적용됐는지 검증한다.
자동 하향·회복 상향·수동 고정·다른 시청자 영향·반복 전환·긴 시청 후 자원 정리를 자동 테스트와 실제 브라우저로 확인한다. 소스 목표 FPS를 조용히 낮추지 말고 파생 화질의 FPS를 다르게 설계했다면 실제 값과 이유를 명시한다.

3. 모바일 시청 대응

최우선은 시청 페이지다. 송출 프로그램은 Windows 데스크톱 앱으로 유지한다. iPhone Safari와 Android Chrome을 주 대상으로 하고, 태블릿·기타 모바일 브라우저는 지원 범위를 명시한다.
360/390/430px 세로 폭, 휴대폰 가로 보기와 태블릿을 확인한다. 사이드바가 영상 폭을 계속 차지하거나 페이지가 옆으로 넘치지 않게 한다. 앱바·채팅·키보드·하단 컨트롤·노치 안전 영역과 실제 보이는 높이를 처리한다. 데스크톱의 현재 배치는 유지한다.
영상은 원본 비율과 전체 내용을 보존한다. 세로 창을 억지로 16:9에 늘리거나 채팅 때문에 영상 가장자리를 자르지 않는다. 회전·주소 표시줄 높이 변화·키보드 표시에도 영상·채팅 입력·모달 버튼에 접근할 수 있어야 한다.
터치에서 hover에 의존하지 않는다. 영상 탭으로 컨트롤 표시, 표시 후 재생/정지, 드래그 탐색·음량, 스크롤과 탐색 충돌, 화질 메뉴 선택을 실제 손가락 조작으로 확인한다. 터치 영역은 대체로 44px 이상을 확보하되 데스크톱 아이콘 디자인은 유지한다.
자동 재생·소리 재생 정책을 처리한다. 필요하면 음소거 시작 또는 명확한 재생/소리 켜기 동작을 제공한다. 소리 없이 재생 중인 상태를 소리까지 성공한 것으로 보고하지 않는다. playsinline과 브라우저 전체 화면 정책, 지원되는 PiP만 처리한다.
현재 H264/Opus WebRTC와 HLS 경로의 코덱·프로파일·오디오 지원을 각각 확인한다. HLS를 추가하면 AAC 등 대상 브라우저가 실제 재생하는 오디오 조합이 필요한지 검증한다. 같은 오디오를 이중 재생하거나 불필요하게 모든 원본을 다시 인코딩하지 않는다.
재생 경로는 기능 감지로 선택한다. Safari의 네이티브 HLS와 MSE/MMS 기반 플레이어 차이를 처리하고, UA 문자열만으로 동작을 보장하지 않는다. hls.js를 선택하면 버전을 고정하고 사용 중인 버전과 브라우저 지원 범위를 기록한다.
라이브·DVR 탐색·실시간 복귀·채팅·화질 변경·전체 화면·재접속을 테스트한다. 모바일에서 기존 DVR가 동작하지 않는다는 이유로 아무 설명 없이 기능을 없애고 모바일 대응 완료로 보고하지 않는다. 지원하지 못하는 조합은 범위를 분명히 표시하고 이유·대체 경로를 기록한다.
백그라운드·화면 잠금 후 복귀, Wi-Fi↔셀룰러 전환과 IP 변경, 통화 등 오디오 중단 후 복구를 확인한다. 배터리 절약과 디코딩 부하도 관찰하고 불필요한 숨은 영상·통계 타이머를 정리한다.
이름 설정·메시지 전송·한글 조합·키보드 열림·모달 스크롤·채팅 자동 스크롤을 확인한다. 입력 중 전역 단축키가 동작하면 안 된다.
뷰포트 에뮬레이션은 레이아웃 시험이다. iOS Safari/WebKit, 실제 휴대폰 디코딩·오디오 정책·Wi-Fi↔셀룰러 전환을 실제 검증한 것으로 보고하지 않는다. 실제 단말이 없으면 그 사실과 재현 가능한 점검 절차를 남긴다.

4. 인터넷 서비스 구조와 재생 프로토콜

URL을 받은 시청자가 클라이언트 프로그램이나 VPN 설치 없이 접속하는 흐름을 목표로 한다. 브라우저에 송출 PC의 사설 IP, localhost, MediaMTX 관리 주소를 그대로 광고하지 않는다.
송출용 로컬 주소, 중계 서버 입력 주소, 공개 시청 base URL과 미디어 ICE 주소를 구분한다. 외부 서버로 보내려면 실제 외부 publish 경로와 인증이 필요하다. 기존 serverHost가 이를 대신한다고 가정하지 않는다.
한 방송 1,000명과 모바일·ABR·DVR를 함께 고려하여 WebRTC, HLS/LL-HLS 또는 혼합 방식을 비교하고 결정 이유를 짧은 설계 기록으로 남긴다. HLS를 넣는다고 자동으로 다중 화질이 생기는 것은 아니며, 실제 화질 스트림과 master playlist/선택 경로를 연결해야 한다.
WebRTC의 낮은 지연, HLS 계열의 브라우저 호환·HTTP 배포, 트래픽·재인코딩 비용을 비교한다. 지연이 늘어나는 경로를 선택하면 측정값과 사용자에게 적용되는 모드를 명시한다. WebRTC 미디어가 일반 웹 터널이나 HTTP CDN으로 그대로 전달·캐시된다고 가정하지 않는다.
원본 한 번 업로드, 화질별 공유 인코딩, 미디어 전송량과 복제 서버/CDN 사용 여부를 구분한다. CDN·다중 서버는 측정한 병목에 맞춰 도입하고 처음부터 무료 1,000명 수용을 약속하지 않는다. 단순히 송출 PC에서 모든 시청자에게 복제하는 구조의 업로드 한계도 측정한다.
HTTPS/WSS, 정확한 프록시·CORS·WebSocket 경로, STUN/TURN·TCP 대체 경로와 네트워크별 도달성을 처리한다. 외부 시청 URL만 열리고 실제 미디어 경로가 막힌 경우를 별도 오류로 구분한다. TURN 자격 증명은 필요한 유효기간·권한으로 관리한다.
시청·송출·관리 권한을 분리하고 공개 서버에 관리 API나 네이티브 시작/중지 명령을 노출하지 않는다. 개인 키·서버 비밀키를 UI·저장소에 넣지 않는다. 초기 시청은 게스트로 가능하게 설계할 수 있으며 전체 소셜로그인 구현을 선행 조건으로 만들지 않는다.
방송 등록·썸네일·목록·채팅·DVR의 URL도 공개 경로와 일치시킨다. 멀티캐스트 탐색만을 인터넷 방송 목록의 기반으로 쓰지 않는다. 같은 공유기 연결과 완전히 다른 인터넷 회선 접속을 별도 검증한다.
필요하면 server/, deploy/, tests/ 같은 소규모 서비스·배포·검증 영역을 추가할 수 있다. C++ 송출 앱과 기존 웹 UI는 보존하고 인터넷 배포 때문에 UI 전체를 다시 만들지 않는다. 실제 서버 계정이나 도메인이 없으면 로컬 재현 구성과 환경 변수 예시·배포 절차까지 만들고 공개 접속은 미검증으로 구분한다.

5. 사용자 요청에 따른 환경 문구 정리

운영 화면의 ‘내부망’, ‘폐쇄 내부망’, ‘폐쇄망’, ‘인트라넷 전용’ 표시와 이를 전제로 한 설명을 제거한다. 중립적인 실제 기능 용어를 사용하고, 외부 접속 성공 여부를 확인하지 않은 ‘온라인/인터넷 연결됨’ 배지로 바꾸지 않는다.
특히 work/console-template.html 상단 environment 영역과 빌드 결과 outputs/index.html의 지구본+‘내부망’을 정리한다. 의미 없는 빈 배지·아이콘·구분선도 남기지 않는다. 소스에서 고친 뒤 빌드하며 생성 HTML만 고치지 않는다.
README.md, native/README.md, packaging/README.txt, START_HERE.txt, UI_HANDOFF.txt와 기존 Claude 지시서의 활성 요구를 인터넷 서비스 방향으로 일치시킨다. ‘외부 서비스 금지’, ‘내부 STUN/TURN만’, ‘인터넷 차단 실행이 반드시 전제’ 같은 과거 제한은 더 이상 필수 요구가 아니다.
보존용 reference/와 reference-v05/ 원본·과거 검증 보고서·Git 이력의 문구까지 몰래 바꾸지 않는다. 과거 자료는 당시 상태 기록으로 표시한다. 현재 UI의 허용 변경은 새 비교 기준으로 검증한다.
실제 로컬 네트워크 접속 지원, 수동 서버 IP/포트, loopback 프로세스 통신, 사설 IP 판별 코드를 단어가 비슷하다는 이유로 삭제하지 않는다. 인터넷 지원과 로컬 접속은 함께 가능하다. 기술 문서의 실제 네트워크 경로 설명은 정확한 상태로 갱신한다.

산출물과 완료 보고

실행 가능한 소스·빌드·배포 설정, 한 명부터 1,000명까지 설정 가능한 부하 스크립트, 네트워크 변화 프로필, 모바일 점검표와 실제 결과를 남긴다. 문서상의 기대 결과와 실행에서 나온 결과를 분리한다.
시험 결과는 재현 가능한 명령·도구 버전·서버 사양·발생기 사양·프로토콜·실제 인원·화질/FPS·대역폭·기간·오류·p50/p95와 함께 CSV/JSON 등으로 제공한다. API 부하·프로토콜 미디어 부하·실제 브라우저 체감·실제 외부망 검증을 별도 결과로 관리한다.
수정 전후 동일 장면(작은 글자, 움직임 많은 화면)의 화질·지연·FPS·부하를 비교한다. 기존 캡처·오디오·DVR·채팅·화질 선택·고정 틀·제목 표시줄 제외·컨트롤 숨김이 유지되는지 확인한다.
FEATURE_BACKLOG.csv의 상태·검증 결과와 실행 결과 문서를 갱신한다. 원본 코드 검토 상태를 실제 통과로 바꿀 때는 근거를 연결한다. 실제 달성 동시 시청자, 최초 병목, 1,000명까지 남은 조건, 미지원 모바일 조합, 추가 비용/자원 필요 여부를 구체적으로 보고한다.
사용자가 별도로 요청하지 않은 P1~P3 기능이나 저장소 푸시를 이번 구현 완료 조건에 추가하지 않는다. 커밋·푸시를 요청받으면 사용자의 dev-kjy → main ff-only 병합 → 작업 브랜치 삭제 절차와 한국어 커밋 메시지 규칙을 따른다.
