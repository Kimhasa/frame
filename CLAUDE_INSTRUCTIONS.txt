현재 작업 우선 지시
사용자 요청으로 UI가 0.5로 변경되었다. UI_HANDOFF.txt와 CLAUDE_FUNCTIONAL_TASKS.txt를 먼저 읽고 현재 UI를 유지한다. 아래 UI 0.4 고정 지시는 새 문서와 충돌하지 않는 범위에서 적용한다. 0.4 원본을 보존하고 새 검사는 tools/verify-ui-v05.mjs를 사용한다.

FRAME Console 실제 구현 지시서

작업 위치
프로젝트 루트는 C:\Users\wlsdu\OneDrive\Desktop\frame 이다. 이 폴더를 작업 디렉터리로 열고 모든 상대 경로를 이 위치에서 해석하라. 현재 UI는 outputs/index.html, 승인된 원본은 reference/index.html과 reference/screenshots/, 작성 소스는 work/에 있다. 이 지시서부터 읽고 해당 폴더 안에서 구현하라.
신규 C++ 호스트 소스는 native/, 빌드 결과는 build/, 실제 배포 폴더는 dist/ 아래에 구성할 수 있다. 기존 UI 작성 소스의 위치와 기준 파일은 유지하라. 개발용 미리보기와 제품 배포를 구분하고, 최종 실행 진입점은 dist/FrameConsole/FrameConsole.exe로 정리하라.

최우선 요구
현재 승인된 FRAME Console 0.4 UI를 시각적으로 그대로 유지하면서 실제로 작동하는 Windows 스트리밍 프로그램을 구현하라. 이 작업은 기존 화면에 기능을 연결하는 작업이다. 사용자는 현재 디자인을 확정했으며 UI 재디자인을 허용하지 않았다.

레이아웃, 색상, Pretendard, 글자 크기와 굵기, 간격, 테두리, 포커스, 아이콘, 자체 선택 메뉴, 슬라이더, 스위치, 모달, 반응형 동작을 임의로 바꾸지 마라. "더 좋아 보인다", "프레임워크에 맞춰 정리한다", "네이티브답게 만든다"는 이유로 변경하지 마라. React, Vue, Tailwind, Qt 위젯, MFC 컨트롤로 화면을 다시 만들지 마라. 브라우저 기본 select와 외부 미디어 플레이어 컨트롤로 대체하지 마라. 데모 표시, 설명 카드, 불릿, 새 대시보드를 추가하지 마라.

기능 연결에 필요한 JavaScript와 C++ 코드는 변경할 수 있다. 실제 창 제목, 서버 주소, 접속 상태, 수치, 오류 내용은 실제 데이터로 바꾼다. 실제 영상과 오디오를 연결하면서 기존 미리보기 영역 내부의 미디어 렌더러를 바꿀 수 있으나, 외부 크기와 레이아웃, 컨트롤은 그대로 유지한다. 실제로 지원하지 못하는 설정은 기존 비활성화 상태와 오류 표시를 사용하고, 성공했다고 꾸미지 마라.

전달 파일의 역할
reference/는 변경 금지 원본이다. index.html, assets/fonts/, screenshots/가 승인된 기준이다. reference/README.txt에는 현재 UI의 구현 범위와 제한이 기록되어 있다.
outputs/는 개발을 시작할 현재 UI 복사본이다. outputs/index.html은 현재 완성된 화면이며 프로토타입이다. HTML, 폰트, 라이선스까지 그대로 열어 확인하라. 이 전달 묶음에는 아직 실제 스트리밍 실행 파일이 없다.
work/에는 원본 UI 작성 소스가 있다. console-template.html, console.css, ux.css, components.css, components.js, console-ux.js를 읽어라. node work/build-console.mjs는 outputs/index.html을 다시 만든다. node work/serve.mjs는 개발용 미리보기이며 제품 실행 의존성으로 사용하지 않는다.
UI_LOCK.json과 tools/verify-ui-lock.mjs는 기준 파일 보존 및 현재 UI의 스타일, SVG, 컨트롤 ID를 검사한다. 이 파일들을 기준을 낮추기 위해 수정하지 마라. 변경 전후 node tools/verify-ui-lock.mjs를 실행하라. 이 검사는 실제 프로그램의 시각적 일치나 스트리밍 성능을 증명하지 않으므로 실행 화면 비교와 기능 검증도 필요하다.

실행 목표
사용자는 FrameConsole.exe 하나를 실행한다. 지금 승인된 화면이 앱 내부에 열려야 한다. 공유할 창을 선택하고 송출 시작을 누르면 실제 창 화면과 선택한 오디오가 송출된다. 다른 PC는 내부망의 시청 주소를 브라우저로 열어 같은 디자인의 수신 화면에서 영상을 본다.
첫 배포는 실행 exe와 필요한 도구, 런타임, UI, 폰트가 들어 있는 한 폴더로 만든다. 폴더 안에서 실행 진입점은 FrameConsole.exe 하나다. FFmpeg와 MediaMTX를 사용자가 별도 콘솔에서 수동 실행하게 하지 마라. 실제 송출은 사용자가 시작을 누른 뒤에 시작한다. 첫 실행만으로 자동 송출하거나 마이크를 자동 녹음하지 마라.

기술 방향
기존 C++ 프로젝트가 있으면 먼저 구조와 개발 도구를 확인하고 유지하라. 신규 프로젝트라면 C++17, MSVC x64, CMake와 Win32 + WebView2를 기본 출발점으로 한다. UI는 현재 HTML/CSS/JS를 그대로 재사용한다. 개발 도구와 실제 지원 Windows 버전, SDK, WebView2 Runtime 버전을 명시하라. "C++17이니 모든 Windows에서 실행된다"고 가정하지 마라.
WebView2 Runtime은 오프라인 배포가 가능한 구성을 마련하라. Fixed Version Runtime 동봉 또는 승인된 오프라인 설치 방식 중 대상 환경에 맞게 선택하고 실제 필요한 파일과 설치 조건을 문서화하라. 런타임 설치 여부를 확인하며 인터넷에서 내려받는 Bootstrapper에만 의존하지 마라. UI 파일을 exe에 넣는 것만으로 WebView2 엔진까지 단일 파일이 되는 것은 아니다.
실제 캡처와 인코딩, 네트워크 처리는 C++ 백엔드에 두고 UI에는 명시적인 요청과 상태 이벤트를 연결하라. WebView2 메시지는 신뢰하는 로컬 UI 출처에서만 받고, 명령 종류와 인수를 검증하라. 임의 명령 실행이나 임의 파일 접근을 노출하지 마라. 비동기로 처리하여 영상 작업 때문에 UI가 멈추지 않게 하라.

캡처
실제 Windows 창을 열거하고 제목, 안정적인 식별자와 미리보기를 제공하라. 같은 제목의 창과 한글 제목, DPI 배율, 여러 모니터, 창 크기 변경을 처리하라. 선택한 창을 확인할 수 있도록 실제 미리보기를 연결하라.
Windows Graphics Capture 등을 우선 검토하고 대상 앱에서 검증하라. GDI 등을 사용하면 지원 범위와 GPU 렌더링 앱에서의 결과를 실제로 확인하라. 가려진 창, 최소화, 창 종료, 원격 데스크톱과 잠금 상태의 제한을 기록하라. 캡처가 끊기거나 지원되지 않으면 기존 상태 및 오류 표시로 알려라. 전체 바탕화면으로 몰래 전환하지 마라.

FFmpeg와 MediaMTX
캡처 영상을 FFmpeg로 인코딩하고 MediaMTX로 전달하라. 외부 FFmpeg 프로세스와 라이브러리 직접 연결 중 필요한 성능과 제어를 만족하는 방식을 선택하여 구현하라. 사용하는 바이너리의 버전, 빌드 옵션, 코덱, 배포 조건과 추가 DLL을 기록하라. 존재하지 않는 FFmpeg 입력 장치나 설치되지 않은 가상 오디오 드라이버를 전제로 구현하지 마라.
브라우저 WebRTC 수신에 맞는 영상 프로파일, 픽셀 형식, 키프레임 및 타임스탬프를 검증하라. 브라우저 WebRTC에서 문제가 되는 H.264 B-frame을 사용하지 마라. 오디오는 브라우저와 MediaMTX가 함께 처리할 수 있는 코덱으로 연결하고 실제 협상을 확인하라.
설정 파일에서 서버 IP, 송출 포트, 시청 관련 포트, 스트림 경로를 관리하라. LAN 클라이언트가 실제 도달할 수 있는 서버 주소를 MediaMTX WebRTC 설정에 반영하라. 폐쇄망에서 외부 STUN/TURN 서버가 항상 필요하다고 가정하지 마라. 필요한 중계가 있다면 내부 구성으로 문서화하라.

같은 UI로 브라우저 수신
현재 시청 주소를 열었을 때 승인된 수신 화면이 나와야 한다. MediaMTX 기본 플레이어나 iframe 기본 화면으로 바꾸어 납품하지 마라. 필요하면 정적 UI 제공과 WHEP 요청 전달을 구성하여 같은 디자인에서 스트림을 재생하라. 실제 포트와 URL은 환경에 맞는 동적 데이터로 바꿀 수 있으나 기존 UI 구성은 바꾸지 않는다.
클라이언트는 서버 IP로 접속한다. 원격 브라우저의 localhost를 송출 PC로 착각하지 마라. 브라우저 수신에는 C++ 개발 환경이나 Node/Python 설치를 요구하지 않는다. 원격 시청자가 송출 PC의 네이티브 명령이나 시작·중지 API를 호출할 수 없도록 경계를 분리하라.
일시정지, 이어 보기, 음소거, 재생 음량, 넓게 보기, 전체 화면 및 연결 종료를 실제 미디어에 연결하라. Space/K, M, T, F 및 기존 선택 메뉴의 키보드 동작을 유지하라. 다른 입력칸의 타이핑이나 방향키 조작을 가로채지 마라.

화질과 프레임
송출 화질 선택지는 240p, 360p, 480p, 720p, 1080p, 1440p, 2160p이며 기본은 1080p다. 프레임은 기본 60fps이며 30, 60, 90, 120, 144, 165fps와 30~165 정수 직접 입력을 유지한다. 비트레이트 자동/수동 설정도 실제 인코더에 연결하라.
이 값들은 목표 설정이다. 144/165fps를 선택할 수 있다는 것과 실제 달성은 구별하라. 실제 원본 주사율, 캡처, 메모리 복사, GPU 인코더, 네트워크와 수신 디코딩 조건을 확인하고 실제 캡처/송출/수신 FPS, 지연, 드롭 프레임을 측정하라. 프레임 복제로 실제 모션 성능을 높였다고 보고하지 마라. 지원하지 못하는 설정을 조용히 30fps로 낮추거나 UI 숫자만 바꿔 성공으로 표시하지 마라. 지원 범위를 기존 오류 방식과 로그로 알리고 실제 적용 설정을 보고하라.
GPU 인코더는 존재 여부와 지원 설정을 확인한 뒤 사용한다. 특정 GPU, NVENC/QSV/AMF나 드라이버가 모든 PC에 있다고 가정하지 마라. 소프트웨어 대체 경로와 그 성능 한계를 구분하라. 캡처/인코딩 큐와 타임스탬프를 관리하여 지연과 메모리가 무한히 쌓이지 않게 하라.
재생 화질 메뉴는 실제로 존재하는 원본 이하 화질에 연결하라. 현재 프로토타입의 캔버스 크기 변경을 다중 화질 전송이라고 보고하지 마라. 실제 여러 화질에는 별도의 인코딩/스트림 구성이 필요하다. 필요한 품질을 켜거나 전환하는 방식과 자원 사용을 설계하고 실제 스트림 전환을 검증하라. 미구현 항목은 기존 비활성화 상태로 처리하고 미완료로 명시하라.

오디오
사용 안 함, 시스템 소리, 마이크, 시스템 + 마이크 선택을 실제 오디오 입력에 연결하라. 시스템 소리는 WASAPI loopback 등 실제 사용할 수 있는 경로를 사용하라. 마이크는 실제 입력 장치와 권한, 샘플레이트와 채널 구성을 처리하라. 두 입력을 선택하면 리샘플링, 믹싱과 영상 동기화를 구현하라.
시스템 소리와 마이크의 음량과 음소거를 독립적으로 적용하고 송출 중에도 변경 가능하게 하라. 수신 플레이어의 음량은 시청자 로컬 재생에만 적용되어야 한다. 시청자가 음소거했다고 서버 전체 송출 음량이 바뀌면 안 된다. 소스별 음량, 혼합, 무음, 반복 음소거, 재연결과 동기화를 실제로 확인하라.

프로세스와 오류 처리
프로그램이 시작한 FFmpeg와 MediaMTX의 수명주기를 관리하라. 종료 시 자신의 자식 프로세스만 정리하라. 이름으로 모든 ffmpeg.exe나 mediamtx.exe를 종료하지 마라. Windows Job Object 등을 검토하여 비정상 종료 때 남는 자식 프로세스도 관리하라.
포트 점유, 잘못된 IP, 캡처 창 종료, 인코더 실패, 오디오 장치 없음, 서버 종료, 수신 실패와 재접속을 처리하라. 현재 UI의 준비/송출/실패/종료 상태를 실제 백엔드 이벤트로 갱신하라. 현재의 setTimeout 성공 시뮬레이션과 가짜 연결 수를 실제 상태로 교체하라. 존재하지 않는 측정값을 만들어 표시하지 마라.
관리자 권한이나 방화벽 전체 해제를 요구하는 해결책으로 만들지 마라. 필요한 프로그램과 포트 허용 사항을 문서화하고 사용자 정책에 따른 설정으로 처리하라. 실행 때 임의로 OS 보안 설정을 바꾸지 마라.

오프라인 배포
개발용 도구와 실행에 필요한 구성요소를 구분하라. 실행 PC에서 인터넷 접속, CDN, 웹 폰트 다운로드, npm install, pip install, 온라인 인증 서버가 필요하지 않게 하라. Pretendard는 현재 로컬 파일과 OFL 라이선스를 그대로 포함한다. C++ 런타임, WebView2, FFmpeg, MediaMTX와 실제 추가 DLL을 빠짐없이 포함하거나 승인된 오프라인 설치 절차로 제공하라.
의존성의 출처, 버전, 해시와 라이선스를 기록하라. 빌드 시 내려받는 의존성도 고정하고 오프라인에서 재빌드할 수 있는 보관 방식을 마련하라. 실행 파일의 위치에 공백이나 한글이 있어도 실행되어야 한다.

작업 순서
먼저 이 지시서와 reference/README.txt, 승인된 화면 및 소스를 읽고 UI 잠금 검사를 통과하라. 그 다음 기존 저장소와 빌드 환경을 확인하고, 현재 UI를 그대로 표시하는 C++ 호스트를 먼저 빌드하라. 실제 창 목록과 캡처, 영상 인코딩 및 중계, 다른 PC 브라우저 수신, 오디오와 품질 설정을 차례로 연결하라. 계획 설명만으로 작업을 끝내지 마라.
임시 데이터는 별도의 개발용 경로에만 두고 배포 프로그램이 조용히 프로토타입으로 되돌아가게 하지 마라. 단계적으로 연결하되 요구된 기능이 남아 있으면 완료라고 표시하지 마라. UI 구조를 바꾸어 구현 난도를 회피하지 마라.

검증과 납품
원본과 같은 client area 크기에서 송출 초기 상태, 창 선택, 준비 상태, 선택 메뉴 열림, 입력 포커스, 오디오 믹서, 오류, 송출 중, 수신, 화질 메뉴와 좁은 화면을 캡처하여 비교하라. 실제 영상 영역, 시간, 실제 창 제목 등 동적 데이터만 비교에서 제외하고 나머지 UI 차이를 확인하라. CSS 해시 통과만으로 화면이 같다고 단정하지 마라.
개발 PC 한 대에서의 성공과 다른 IP를 가진 별도 PC의 수신을 구분하여 검증하라. 인터넷이 끊기고 개발 도구가 없는 깨끗한 환경에서도 실행을 확인하라. 해상도/프레임별 실제 성능, 오디오 동기화, 복수 시청자, 창 크기 변경, 실패 후 재시작과 앱 종료 후 남는 프로세스를 확인하라. 원격 PC나 실제 내부망이 없으면 그 항목을 미검증으로 명시하고 실행 절차와 진단 로그를 제공하라.
최종 산출물은 C++ 소스와 CMake 구성, 빌드 명령, 실행 가능한 배포 폴더와 ZIP, 설정 예시, 의존성/라이선스 목록, 검증 결과와 실행 화면이다. UI 변경 여부, 실제 검증한 환경, 지원한 코덱과 FPS, 남은 제한을 명확히 보고하라. 빌드 도구 부족 등으로 exe를 만들지 못했다면 소스나 화면만으로 exe 완성이라고 말하지 마라.

Git 규칙
저장소가 있으면 시작 전에 현재 브랜치, 미커밋 변경, 원격, worktree 상태를 확인하고 무관한 작업을 보존한다. 커밋·푸시를 진행하는 경우 기본 작업 브랜치는 정확히 dev-kjy, 원격은 origin, 통합 브랜치는 main이다. origin을 fetch하고 main을 --ff-only로 갱신한 뒤 최신 main에서 작업 브랜치를 시작한다. 기존 dev-kjy에 미병합 작업이 있으면 보존하여 이어서 작업한다. 구현과 검증, 작업 커밋은 dev-kjy에서 진행한다.
병합 전에 원격 main을 다시 확인하고 필요하면 아직 공유하지 않은 커밋만 최신 main 위로 rebase하여 재검증한다. 공유된 이력은 보존하며 강제 푸시하지 않는다. dev-kjy 푸시 후 main에서 git merge --ff-only dev-kjy, main 푸시 순서로 진행한다. 원격 main에 작업 커밋이 포함된 것을 확인한 뒤 해당 원격 작업 브랜치와 로컬 dev-kjy를 삭제하고 main에서 마친다. 로컬 삭제는 git branch -d다. 커밋·푸시의 실행 범위는 사용자의 해당 작업 지시를 따른다.
커밋 제목은 type : 한국어 메시지 형식이며 콜론 양쪽에 공백 하나를 둔다. 빈 줄 다음에 - 로 시작하는 구체적인 한국어 변경 목록을 적는다. 실제 줄바꿈이 있는 메시지 파일을 만들고 git commit --file로 전달한다. 작업과 관계없는 변경을 섞거나 다른 작업의 브랜치를 삭제하지 않는다.

가장 중요한 완료 조건
현재 UI를 그대로 쓰면서 실제 다른 PC가 영상을 볼 수 있어야 한다. UI 재디자인, 프로토타입 숫자 변경, 계획서만 작성한 상태는 완료가 아니다.
